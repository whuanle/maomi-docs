### 1. 章节大纲

- **H1 + 引言**：从"多轮对话 token 成本爆炸"切入（前几章解决了消息/工具/循环/subagent，但每轮都重发几十万 token 是隐性成本杀手），点出三个加粗痛点：①前缀必须字节级稳定才能命中；②压缩会破坏前缀；③不同 provider 缓存机制不同（手动断点 vs 自动）。给出"读完这一章你应该能回答……"学习目标。
- **## 一、缓存命中到底在缓存什么**：讲清 Anthropic 手动 `cache_control` 断点（4 个上限、ephemeral 5m/1h）vs OpenAI 隐式自动缓存（前缀匹配）两大范式；mermaid 画"前缀树"图说明命中条件（字节级前缀一致）；讲最小 token 数（Anthropic 1024 起）、写缓存 1.25x/读 0.1x 的经济学。
- **## 二、OpenCode：手动断点的教科书实现**（核心章，源码最完整）
  - 讲 `cache-policy.ts` 的 `auto` 策略：三处打点（最后一个 tool / 最后一个 system part / 最新 user message）
  - 源码：`RESPECTS_INLINE_HINTS`（OpenAI/Gemini 跳过）、`anthropic-messages.ts:234` 的 `ANTHROPIC_BREAKPOINT_CAP=4` + 共享计数器静默丢弃、5m/1h TTL 选择
  - mermaid 画"agent loop 内一轮多调用都命中前缀"的时序
- **## 三、Microsoft Agent Framework：不打断点，靠结构保前缀**（外包给底层 + compaction 保前缀）
  - system instructions 永远最前（`ChatClientAgent.cs`）
  - compaction 不变量："System groups 永不被排除"，列出 Truncation/SlidingWindow/ToolResult/Summarization 四种策略如何保留前缀
  - 关键：summary 插入到被摘要 group 的原位置，前缀字节序列仍稳定
- **## 四、Codex：自动缓存 + prompt_cache_key + 严格保前缀的压缩**（最精细）
  - `client.rs`：`prompt_cache_key = session_id` 让同会话共享缓存槽；websocket 复用判断含 cache key 一致性
  - `compact.rs:305` 那行经典注释 "Trim from the beginning to preserve cache (prefix-based)"
  - compaction 三阶段（Pre-turn `DoNotInject` / Mid-turn `BeforeLastUserMessage`）+ `insert_initial_context_before_last_real_user` 保前缀
- **## 五、横向对比**：大表格（缓存范式/是否打点/断点位置/上限/前缀稳定手段/压缩机制/压缩如何保前缀/配置项/计量）+ mermaid 三家策略映射图
- **## 六、上下文压缩后如何继续命中**（用户特别关注的点，单独成节深挖）
